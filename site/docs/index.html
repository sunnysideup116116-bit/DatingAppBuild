HOW TO READ

先看邊界，再看流程。

這個系統不是單純的「前端呼叫一個後端」。帳號、貼文與檔案有 Appwrite 直連路徑；聊天、配對、AI、行事曆與語音則經由固定公開網域進入 Server。不同資料域有不同 owner，這是閱讀全部文件時最重要的前提。

本頁是公開閱讀版，整理自工作區的 docs/system。它不包含密鑰、密碼、token、cookie 或真實個資；程式碼能證明的內容、合理推論與仍待部署環境確認的事項會分開標示。

00.5

GETTING STARTED

開始閱讀與啟動前提

系統由 Flutter DatingApp、四個後端執行單位與多個外部資料／模型服務組成；只讀程式碼不需要先啟動全部服務。

展開閱讀

若要做實際操作驗證，Server 必須透過 start_all.sh 啟動，前端則需要 Flutter SDK、相依套件與平台工具。本機啟動成功不等於 Appwrite、MongoDB、Neo4j、模型供應商與 Google Calendar 已可用。

01

ARCHITECTURE

整體概觀與 C4 架構

Folks Dating System 以 Flutter App 為使用者入口，以 Social API 為主要產品後端，再由 Risk、Matchmaker、Guardrail 與 Agent runtime 支援。

展開閱讀

DatingApp 負責畫面、導航、Session、快取、API client、即時訊息與語音操作；Server 以 Social 組裝聊天、配對、行事曆、Google Calendar、語音、關係記憶與摘要路由。外部邊界包含 Appwrite、MongoDB、Neo4j、Firebase／FCM、Google Calendar 與模型供應商。

02

REPOSITORIES

Repository 與模組導覽

工作區包含兩個獨立 Git repository：Server/ 是 Python/FastAPI 後端，DatingApp/ 是 Flutter/Dart 前端。

展開閱讀

Server 的主要領域以資料夾與服務埠分開，DatingApp 則以 lib/pages、lib/services、lib/widgets 與原生平台資料夾組成。目錄名稱只提供導航，真正的責任要以入口、註冊與呼叫關係確認。

03

CLIENT

DatingApp 前端架構

DatingApp 是 Flutter 多平台 client，將畫面、session、API adapter、Appwrite SDK、快取、推播與語音互動組合成帳號範圍的使用者體驗。

展開閱讀

啟動時會初始化 Flutter binding、Appwrite 與 Windows 視窗，再非同步初始化 Firebase；登入後的主要頁面由 MainPage 組成，並透過 AppDataCoordinator 預熱 profile、contacts、posts、calendar 等資料。頁面狀態不能取代後端 canonical state。

04

IDENTITY

身分驗證與個人資料

前端使用 Appwrite Account 處理 email/password 與 Google OAuth，並以 Database／Storage 保存或讀取個人資料與檔案。

展開閱讀

身分驗證、profile document 與 Server 端 owner proof 是不同層次；成功登入不等於所有後端能力都已授權。Agent API 會在 HTTPS、正式網域、線上 session 且 user id 相符時附加 Appwrite JWT。

05

AGENT

阿月與 Agent

阿月分成公開 runtime 與私人媒婆 runtime：公開對話走 Public V3，私人悄悄話由獨立 Private V2 runtime 負責。

展開閱讀

公開 Agent 的流程是 Context → Planner（DAG）→ Sub-agents（Guard + Tool）→ Synthesizer → Final。DatingApp 以 NDJSON stream 傳送訊息與互動選項；公開與私人 runtime 可以共用 domain service，但 context、privacy namespace、tool policy 與 trace 不可互相滲透。

06

MATCHMAKING

配對與關係建立

配對由 Social 維護狀態、由 Matchmaker 產生候選／活動訊號；「找到候選」與「使用者做決策」是兩個分開的步驟。

展開閱讀

前端先請求配對搜尋，再取得狀態卡片，最後以 expected status、revision、namespace、explicit reasons 與 idempotency 送出接受或拒絕。timeout 或 graph unavailable 會轉成明確的 pipeline error，而不是模糊地視為沒有候選。

07

SAFETY

聊天與風險治理

雙人聊天的文字訊息必須先經過風險政策，再決定是否保存與讓接收者看見；圖片訊息會走不同的投影分支。

展開閱讀

Social 以 MongoDB 作為聊天資料主要寫入路徑，並非同步鏡像部分訊息到 Appwrite Realtime；DatingApp 同時支援 polling 與 Realtime。風險結果包含 delivery、level、介入指令與回饋資料，不能只用一個 boolean 表示。

08

VOICE

語音互動

系統有註冊語音與 App 內語音兩種能力；App Voice 會先取得 capability，再建立帶有 consent 與 client binding 的 session。

展開閱讀

Server 會驗證 origin、ticket、client binding、quota 與 authenticated session。語音 action executor 只協調既有的 Auth、Chat、Matchmaking、Calendar 與 Agent service，不直接成為另一套 domain state owner。

09

MEMORY

記憶、摘要與圖譜

短期對話、profile memory、relationship context、摘要與圖譜投影是不同資料域，透過 bounded context API 提供給 Agent。

展開閱讀

Mongo preview、Neo4j／graph memory 與 Appwrite data projection 不能互相取代。每個 memory write 都需要 owner、evidence、confidence、source 與 idempotency；正式 graph schema、索引與資料量仍需部署環境補查。

10

CALENDAR

活動、約會與行事曆

個人行事曆、雙人約會協調、Google Calendar 整合與活動探索是不同流程，各自有明確的狀態與授權邊界。

展開閱讀

前端使用 expected revision 更新或取消事件；Server 由 calendar／relationship date services 擁有狀態；Google Calendar 另外處理 OAuth callback、status、list 與 disconnect。阿月只能讀取受限的 calendar projection，不應把未授權資料直接寫成永久偏好。

11

SOCIAL

社群、貼文與媒體

社群功能由 DatingApp 直接使用 Appwrite Database 與 Storage 保存貼文、圖片和媒體 metadata；通知與部分 profile／relationship API 由 Social 提供。

展開閱讀

聊天附件、profile image 與貼文使用不同 bucket，降低權限與 cache 混淆。Push notification 只傳遞 allowlisted data，例如 chat surface、conversation id、destination room 與 focus match id，不讓 listener 自動執行配對決策。

12

CONTRACTS

API 與資料契約

前後端契約分成 HTTP JSON、NDJSON stream、WebSocket event、Appwrite SDK document 與 push payload 五類。

展開閱讀

每一類都有自己的 owner、timeout、錯誤碼與狀態語意。重要欄位包括 user／owner、client message id、match revision、coordination revision、stream protocol version、choice／confirmation 與 allowlisted notification references。

13

RELIABILITY

背景工作與可靠性

Social 啟動時會建立索引並啟動多個 worker、scheduler、outbox 與 background task；API response 成功不一定代表所有 side effect 已完成。

展開閱讀

可靠性設計集中在 bounded timeout、idempotency、revision、outbox、retry、session epoch 與可觀測 error code。前端 AppDataCoordinator 則以 warmup、cache TTL、resume cooldown 與 owner／epoch gate 避免重複或過期讀取。

14

DEPLOYMENT

部署、啟動與環境

Server 的正式啟動契約是 start_all.sh；固定服務埠為 Guardrail 8081、Risk 8001、Matchmaker 9001、Social 8000。

展開閱讀

啟動腳本依序等待各服務健康檢查，再啟動完整 Social。DatingApp 的正式 API 預設網域是 https://service.misproject.us.ci；程式碼內的啟動順序與正式主機實際部署拓撲要分開看待。

15

TESTING

測試與驗證

兩個 repository 都有 unit、contract、integration 與 workflow 驗證，但測試存在不等於所有流程在目前環境通過。

展開閱讀

Server CI 檢查 Python dependencies、bash -n start_all.sh 與 offline suites；DatingApp 有 Dart tests、integration tests、Flutter analyze 與多平台 build。正式文件應同時記錄覆蓋、執行前提、未執行項目與 production smoke test 缺口。

16

EVIDENCE / LIMITS

證據、限制與待釐清事項

這套文件是以 repository 原始碼與設定做的靜態、來源導向盤點；它不能取代 live deployment、外部 schema、瀏覽器、實機或正式帳號驗證。

展開閱讀

觀察、推論與未知分開記錄。Dart、cross-language property、超大流程與大檔案存在分析工具缺口；正式環境行為、外部供應商可用性與所有端到端流程，都應再以 runtime evidence 逐項確認。
